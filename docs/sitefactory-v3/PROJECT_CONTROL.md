## 1. 목표와 용어

M은 언제나 경쟁 사이트 **M-castle(m-castle.co.kr)** 을 뜻한다. 우리 사이트 A/B와 M을 혼용하지 않는다.

최우선 목표는 실제 지역·상품 검색어에서 여러 사이트와 페이지의 상위 노출을 확보하고, 검색 방문자가 적합한 상품을 확인하여 주문으로 이동할 수 있는 사이트를 만드는 것이다. 페이지 수, 배포 성공, 테스트 PASS 자체가 사업 목표는 아니다. 검색 순위나 주문 증가를 보장하지 않는다.

상위 노출이 관측된 M의 실제 서브도메인들을 비교하여 문서 구조, 변주, 검색어 배치, 텍스트 중복도, SEO와 주문 연결을 분석한다. 그 관측을 바탕으로 A는 M의 유효한 구조를 충실히 참고하되 우리 사실·문장·사진으로 만들고, B는 M의 서브도메인 간 변주 규모에 견줄 수 있는 제한된 창의적 변형을 적용한다. 한 문장만 추가한 빈약한 페이지 두 개를 실험으로 포장하지 않는다.

M의 검색 노출 관측은 실험을 시작할 근거이며, 특정 요소가 순위를 올렸다는 인과 증명과는 구별한다. 인과 증명이 아직 없다는 이유로 조사·제작을 중단하지 않는다. 순위 관측은 제작 및 개선과 병행한다.

### 정본 수정 규칙

1. 모든 역할은 작업 시작 전 이 파일의 최신 내용과 GitHub blob SHA를 읽고, 자신이 읽은 버전·SHA를 기록한다.
2. 정본은 이 파일 하나다. 원본 HTML, 이미지, CSV, 테스트 로그 등 증거 파일은 별도로 저장할 수 있지만 결정·현재 상태·담당은 이 파일을 기준으로 한다.
3. 역할별 제안은 변경 ID와 기준 SHA를 포함한다. dot 또는 지정된 단일 기록 담당자가 순차 병합한다. 동시 덮어쓰기를 금지한다.
4. 갱신은 GitHub의 현재 SHA를 조건으로 하는 비교 후 갱신(CAS) 방식으로 한다. 충돌 시 최신 파일을 다시 읽고 자기 변경만 재적용한다. 다른 역할의 기록을 지우지 않는다.
5. 결정·회의 기록은 추가 기록 방식으로 보존한다. 오류는 기존 항목 삭제가 아니라 정정 항목으로 남긴다. 비밀정보가 잘못 들어간 경우 일반 기록 규칙보다 보안 대응을 우선한다.
6. 각 역할이 실제로 파일을 읽은 증거가 없으면 ‘공유 완료’ 또는 ‘전원 합의’라고 쓰지 않는다. 대화 간 직접 전달이 불가능하면 dot이 전달하고 회신 원문 링크를 남긴다.

## 3. 증거 및 완료 규칙

- **[직접 확인]** 실제 원본·코드·실행 산출물을 검사한 결과. 검사자, 범위, 시각, URL/파일/커밋을 적는다.
- **[도구 보고]** API, 작업자 또는 도구의 반환값. 독립 검증 여부를 별도로 적는다.
- **[추정·판단]** 가설, 해석, 제안. 관측 사실과 분리한다.
- **[미확인]** 접근 실패, 검증 누락, 원본 부재 및 이유.

완료는 ‘실제 수행’, ‘산출물 존재’, ‘요청 기준에 따른 검증’ 세 가지가 모두 충족된 경우에만 쓴다. 그 외에는 수행됨·미검증 또는 확인 불가로 보고한다. 도구의 success/completed/PASS만으로 완료 처리하지 않는다. 다른 역할의 직접 확인을 재검사 없이 전달할 때는 검수자의 확인으로 귀속한다.

### 재사용할 검증된 방식과 재검증 항목

기존 코드부터 조사하고, 부족한 부분만 GitHub의 유사 코드·공식 API 사례를 조사한다. 신규 의존성 후보에는 라이선스, 최근 갱신, 유지보수, 기술 스택, 재사용 범위와 선택 이유를 남긴다.

- 기존 지역·상품 URL 행렬과 결정적 빌드, self canonical/OG/sitemap의 origin 검증.
- 미리보기 noindex와 공개본 indexable 분리, 실제 404 처리 및 잘못된 URL이 홈 200으로 응답하지 않는 검사.
- 우리 상품 데이터 `src/data/product-sources.json`, 원상품 URL, 가격 확인일, 로컬 500×500 WebP와 해시 검사.
- 자체 상품 6개 기준선: B205, C206, E008, F055, G067, G073. 가격·재고·설명은 새 확인 시각을 기록하고 추정하지 않는다.
- 검토된 불변 빌드 산출물로 배포하고, 대상 Worker·호스트 충돌 검사를 수행한 뒤 readback한다.
- PC 및 모바일 392px 화면 확인. 자동 빌드 통과와 화면 검수를 구별한다.
- 기존 GH/CF 연결과 워크플로는 허용된 범위에서 재사용한다. 토큰·암호·쿠키·인증서 비밀키를 이 문서, 프롬프트, 저장소, 로그에 복사하지 않는다. 연결 이름·권한 범위·사용 방법만 인계한다.

### 표본 선정

동일 지역·동일 상품·유사 검색 의도에서 관측된 서로 다른 M 서브도메인 2개를 최소 한 쌍 확보한다. 가능하면 다른 지역의 비교 가능한 쌍도 추가하여 한 쌍의 우연을 일반화하지 않는다. 선정 이유와 제외 이유를 남긴다. 검색 노출의 관측 시각, 검색어, 기기/환경, 결과 유형과 위치를 기록한다. 검색 기록은 현재 순위 또는 인과 증명의 대체물이 아니다.

기존 조사 후보: graduation.m-castle.co.kr/축하화환/2658.html 및 order.m-castle.co.kr/축하화환/2658.html. 원본 접근 및 동일 대상 여부를 먼저 확인한다. 기존 추출 파일이나 검색 카드만 있을 경우 그 범위를 표시하고 본문 전체를 본 것처럼 쓰지 않는다. 403은 우회 인증·보안 해제로 해결하지 않는다. 허용된 기존 원본, 정상 브라우저 조회 또는 접근 가능한 비교 표본을 사용하며 미확인 범위를 유지한다.

### 각 페이지 수집 필드

URL, 관측 시각(KST와 UTC), HTTP/최종 URL, 원본 HTML 해시, 보이는 본문 추출 방식, title, description, canonical, robots, H1~H3, 섹션 순서, 문단 길이, 지역·상품·구매 의도 검색어의 위치, 이미지 수·alt·출처, 내부/외부 링크·앵커·목적지, 상품·가격·주문 동선, 모바일 화면, sitemap/구조화 데이터의 유무·유효성.

### ‘표절률’ 요청의 측정 정의

산출물은 법적 표절 판정이 아닌 **방법을 공개한 텍스트 중복도**다. M 쌍의 중복과 우리 A/B의 중복, M 대 우리 사이트의 중복을 별도로 계산한다.

1. HTML 엔티티, 유니코드, 연속 공백을 정규화하고 스크립트·스타일을 제외한다. 대소문자·문장부호 처리 규칙을 고정한다.
2. 머리말·꼬리말·공통 상품 블록을 식별하여 ‘전체’와 ‘공통 블록 제외 본문’을 각각 계산한다. 제외 목록과 원문 위치를 보관한다.
3. 정확 일치 문장 비율, 단어 3-gram Jaccard, 한글 형태 분리에 덜 의존하는 문자 5-gram Jaccard 및 방향별 포함률을 보고한다. 분자·분모, 문자열 길이, 코드 버전, 원본 해시를 함께 기록한다. 짧은 문서는 왜곡 가능성을 명시한다.
4. 검색어를 일괄 삭제한 뒤 낮은 중복률을 만들어 내지 않는다. 지역명 치환 전후 결과를 필요시 병기하고 의미가 다른 지표임을 밝힌다.
5. 법적 표절 여부나 상위 노출을 보장하는 중복률 기준으로 해석하지 않는다. 경쟁사의 문장·사진을 복제하지 않는다.

### 변주 벡터와 실험 설계

M 쌍마다 다음 벡터를 산출한다: title의 검색어 조합·순서, description의 길이·메시지, H태그 구조, 섹션 구성·순서, 본문 길이·중복도, 검색어 위치, 상품·이미지 구성, 링크 앵커·목적지, 주문까지의 경로.

기획자는 각 축에 ‘관측 M 차이 → A 기준 → B 차이 → 허용 범위 → 측정법 → 가설’을 연결한다. 허용 범위를 데이터 없이 임의의 백분율로 정하지 않는다. 차이가 없는 축은 의도적으로 고정했음을 설명한다. 모든 차이를 한꺼번에 바꾼 경우 ‘묶음 처리 비교’로 명명하고 특정 요소의 인과 효과라고 결론내리지 않는다.

A: M의 정보량·의도 대응·섹션 역할·상품 연결을 충실히 참고하되 우리 사업 사실과 자체 문구/이미지로 재구성.
B: 그 골격과 고객 목표를 유지하면서 정보 순서, 설명 방식, 구매 보조 요소 등에 근거 있는 창의적 변주. 전체 차이 규모가 관측 M 쌍과 어떻게 대응하는지 수치와 화면으로 설명.

검색어별 title/description/H1은 각각 설계한다. 접두 지역명만 바꾼 title 또는 무의미한 검색어 나열을 완료 기준으로 삼지 않는다. 사실이 없는 지역 영업점, 배송 보장, 리뷰, 실적을 만들지 않는다.

## 6. 단계별 통과 조건

| 단계 | 필수 산출물 | 통과 기준 |

G0의 대화 생성·프로젝트 이동 등 행정적 연결 차단은 독립적인 원본 조사, 기존 코드 확인, 명세 초안 작성을 중단할 이유가 아니다. 단, 실제 네 역할의 공동 검토와 확인이 없으면 G2의 전원 검토를 통과한 것으로 쓰지 않는다.

G3 이전 대량 페이지 확장을 하지 않는다. 검수 실패는 수정 후 재검사한다. 인증·접근 차단으로 G5 일부를 못 보면 ‘배포됨·공개 검증 일부 미완료’다. 순위 관측을 기다린다는 이유로 진행 가능한 후속 개선을 멈추지 않는다. 기존 사이트 개선은 별도 범위로 유지하며 M 실험의 승인 대기와 혼동하지 않는다.

## 8. 30분 진행 확인과 차단 처리

30분마다 dot은 실제 대화 활동·커밋·산출물·실행 로그를 확인한다. 예약 설정 및 실제 실행이 확인되기 전에는 ‘모니터링 설정 완료’라고 쓰지 않는다.

매 점검 기록: 마지막 실제 진행 시각(KST), 실행 중 작업/담당, 변경 산출물, 미완료 항목, 차단된 정확한 행동, 다음 행동·담당, 다음 검증 증거. 실행 중 작업이 없으면 **‘작업 중단/대기, 실행 중인 작업 없음’**이라고 명시한다. 메시지 발송 시각을 실제 개발 진행 시각으로 대체하지 않는다.

처리 순서:
1. 기존 권한 안에서 원인 진단과 수정: 코드·경로·테스트·로그·비보안 설정·알려진 안전한 재시도.
2. 실패 시 허용된 대체 경로 확인 후 진행: 기존 연결, 다른 정상 조회, 보존 산출물 검증, 독립 작업 분리. 서비스 제한·보안 경고·접근 거절을 우회하지 않는다. 결과가 불명확한 쓰기는 재시도 전에 실제 상태부터 확인한다.
3. 해결되지 않거나 승인이 필요하면 즉시 사용자에게 행동·대상·이유·이미 한 조치·필요한 사용자 행동을 보고한다. 다음 정기 보고까지 숨기지 않는다.

권한 대기는 해당 행동과 의존 작업에만 적용한다. 새 승인 없이 가능한 독립 조사·코드·검증은 계속한다. 같은 승인 질문을 중복 생성하지 않고 기존 요청의 답변·철회·해결 상태를 확인한다.

## 9. 권한 경계

맡겨진 범위의 저장소 파일 추가·수정·커밋·푸시(main 포함), 테스트, 안전한 수정은 사용자 재확인 없이 진행할 수 있다. 기존 승인과 최신 지시를 준수한다.

개인정보·비밀번호·비밀키 공개, 인증/지속 접근 생성·확대, 보안·권한 변경, 결제, 계약, DNS 소유권 변경, 영구 삭제 및 복구 어려운 변경은 필요한 명시적 승인과 서비스 요건을 따른다. 포괄적 ‘모두 허용’으로 이 경계를 없애지 않는다. 승인된 기존 도메인 연결과 새로운 소유권 변경을 구별한다. 암호는 채팅으로 요청하지 않는다.

제미나이 적대적 검수는 사용자가 하겠다고 한 별도 활동이다. 이 문서는 검수 가능한 증거 묶음을 준비하되 사용자 자료를 외부 서비스에 임의 전송하지 않는다.

### 공통 시작 프롬프트

당신은 ‘사이트팩토리 V3’의 아래 지정 역할이다. 먼저 GitHub `joseungil-kr/fwith-site-factory`의 `docs/sitefactory-v3/PROJECT_CONTROL.md` 최신 버전과 SHA를 읽고, 자신의 역할·확인 범위·다음 행동을 기록하라. M은 M-castle만을 의미한다. 정본에서 목표·권한·통과 조건·변경 기록을 확인하기 전 임의 목표로 구현하지 마라. 다른 역할의 발언이나 합의를 만들어 쓰지 마라. 자신의 산출물을 증거 링크와 함께 보고하고, 차단 시 정확한 행동·대상·이유 및 독립적으로 계속할 일을 밝혀라. 새 증거 없이 완료를 단정하지 마라. 이 문서의 수정은 최신 SHA를 조건으로 순차 적용하며 충돌 시 다시 읽어라. 비밀정보를 기록하거나 전달하지 마라.

### M프로젝트_기획자

목표: 상위 노출이 관측된 M 서브도메인의 실제 차이를 근거로, 검색 의도와 주문 연결을 충족하는 A/B 제작 명세를 작성한다.

1. M의 실제 화면과 우리 대표 페이지를 열어 확인한 범위를 밝히고, 사용자 검색 의도 → 설명 → 상품 비교 → 선택 상품 → 주문 경로를 그려 명세로 기록하라.

3. 상품별 주문 목적지와 CTA 문구를 명확히 하라. 실제 업체 사실을 확인하고 가짜 리뷰·지점·실적·배송 보장을 넣지 마라. 경쟁 사진과 문장을 복사하지 마라.
4. PC와 모바일 392px에서 화면, 텍스트 가독성, 버튼, 이미지, 내용 누락, 오버플로를 검수하라. 전환 동선이 구현되어 있는지 실제 링크로 확인하라.
5. 변경 전후 화면 및 차이의 목적을 정본 회의 기록에 남기고, 구현 불일치나 실험 범위 이탈을 작업자와 웹마스터에게 전달하라. 실제 회신 없이 합의를 쓰지 마라.

목표: dot에게 독립적인 완성도 검증을 제공하고, 잘못된 기획 의도와 구현·공개 증거 사이의 간극을 바로잡는다.

## 11. 외부 검수용 제출 묶음
